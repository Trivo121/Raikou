# Raikou Optical · Phase 0 on Google Colab

Trains a 5-class India land-cover model on **OlmoEarth v1.2 Base**, then calibrates, benchmarks and exports it for the g4dn box. There are three notebooks, and each switches to the cheapest runtime that can do its job:

| Notebook | Runtime | Does | Time (estimate) |
|---|---|---|---|
| `notebooks/01_build_dataset_cpu.ipynb` | CPU, High-RAM | 100 tiles × 3 seasons of Sentinel-2 from Planetary Computer, WorldCover labels, consensus cleaning | 2–3 h, resumable |
| `notebooks/02_train_gpu.ipynb` | L4 GPU (or A100) | fine-tuning, validation at T=1 and T=3 | ~4–6 h on L4 at patch 4 (measured by the speed probe before you commit) |
| `notebooks/03_t4_parity_calibrate_export.ipynb` | T4 GPU | temperature scaling, held-out benchmark (fp32 vs fp16), Visakhapatnam demo bundles, release export | ~1–1.5 h |

The code lives in `raikou_phase0/`. The notebooks are thin; every setting is in `raikou_phase0/config.py`. The notebook cells are generated by `tools/make_notebooks.py`: edit the cells there and regenerate, rather than editing the `.ipynb` files.

> **These scripts have not been executed.** The laptop has no numpy or torch, so everything was checked for syntax and cross-module references only, and the encoder calls were written against the `olmoearth-pretrain-minimal` 0.1.2 source. Each notebook therefore starts with a self-test that takes seconds on that notebook's runtime. Run it before anything else.

## What changed from your plan, and why

Everything not listed here follows your plan as written. That covers:
- the 100 tiles, 6 zones and per-zone counts, and the 70/15/15 tile split with Visakhapatnam and a Karnataka tile locked into test;
- the three season windows, the band order and the DN harmonization;
- the class remap: mangroves → forest, shrubland → natural vegetation, moss → barren;
- your index thresholds for built-up, cropland, barren and water;
- the temporal attention pooler, the 10 m stem and the U-Net fusion;
- T-dropout at 40/20/40, rotation, flips and ±5 % jitter;
- 0.5 weighted CE + 0.5 Dice with your class weights;
- LLRD 0.65 at 2e-4, weight decay 0.02, 35 epochs (3 of warmup), cosine down to 1e-6, and the best checkpoint chosen on mean(mIoU T1, T3);
- 128/64 Gaussian blending, the 4 px sieve and temperature scaling;
- the T4 fp16/fp32 check, the GIS bundle, the Visakhapatnam run and the Drive → g4dn transfer.

| Your plan | In these scripts | Why |
|---|---|---|
| 2025–26 imagery with WorldCover **2021** labels, then filter what changed | **2020–21 imagery** (Oct 2020 → May 2021); `TRAIN_HYDRO_YEAR` in config.py switches it back | Labels and images must come from the same year. Otherwise the filter mixes real change with WorldCover errors, and real change on test tiles is scored as model error. The model is applied to current imagery at inference. |
| `patch_size = 2` (20 m tokens), batch 16 | **`patch_size = 4`** by default; 2 is one setting away | Patch 2 means 12,288 tokens per T=3 chip, which costs roughly 6–8× the compute. Batch 16 won't fit in an L4's 22.5 GB. Your "~6 min per epoch / ~4 h" matches patch 4. The 10 m stem is what carries the sharp edges. |
| BatchNorm in the decoder | **GroupNorm** | Inference runs 1–8 windows at a time, and patch 2 trains in micro-batches of 4. Batch statistics are unreliable in both cases. |
| Clearest pass by granule cloud ≤ 15 % | The 6 least-cloudy dates are re-checked with the **SCL over the tile itself**, and the clearest is used | A granule's cloud percentage says little about a 10 km tile. |
| Fixed chips (stride 96) packed into 10 tar shards, 12–15 GB | One compressed `.npz` per tile (~4–5 GB total) and **fresh random crops** every epoch (100 per tile) | Same crop count, more variety, 100 files instead of thousands, and resumable per tile. |
| One rule for all natural vegetation (NDVI max ≥ 0.45 and min ≥ 0.22) | Separate rules for tree, shrub, grass and mangrove, plus a **retention report** per class and zone | Scrub, grassland and leaf-off deciduous forest fall below 0.22 in April–May. "Natural vegetation" would otherwise be learned from evergreen canopy only. |
| Consensus and boundary filtering on every split | **Train and validation only.** Test and calibration use the unfiltered `label_raw` (filtered scores are reported too) | Filtering a test set down to the pixels that already agree with a rule inflates its scores. |
| UTM EPSG:32643/44/45 | **32642–32647**, chosen from each tile's centre | Kutch and Jaisalmer (your arid tiles) are in zone 42N. |
| Snow not handled | SCL 11 is masked and WorldCover 70 is ignored | The Ladakh tiles. Production treats snowy AOIs as out of domain. |
| "Overall Accuracy", "2021-vs-2026 transition matrix" | **"Agreement with WorldCover-derived labels"**, and an **agreement matrix** printed next to the held-out disagreement rate | This follows the approved plan. WorldCover itself is 76.7 % accurate, and off-diagonal area mixes real change with both maps' errors. |
| Softmax as "confidence %" | Temperature fitted on validation tiles against unfiltered labels. The meaning is written into every bundle. | A score of 80 means about 80 % of such pixels agreed with WorldCover on held-out tiles. |
| Cloudy tokens "masked out in self-attention" | Tokens under 50 % clear are marked `MISSING`, following AI2's own rslearn wrapper. The scripts also fix eval-mode batch padding, and the self-test checks that fix. | Without the fix, padded tokens leak into shorter samples when windows are batched at inference. |
| `LayerDecayAdamW` | AdamW with per-layer parameter groups, using the same LRs as your table; embeddings sit one step below block 0 | I found no class of that name in rslearn. The paper's App. C describes exactly this schedule. |
| Base weights from the ModelScope link | Hugging Face or ModelScope; either way the **SHA-256 is checked** | The two are byte-identical (`57f7b66f…88deec`), but the mirror carries no licence file. The export bundles AI2's licence. |
| `g4dn.xlarge` | It's a **g4dn.2xlarge** | Same T4 GPU, so the parity results hold. |

The Copernicus/Planetary Computer parity check is the optional last section of Notebook 1, at about 50 processing units. It matters for production imagery, not for the 2020–21 training data.

## Before you start

1. **Copy the code to Drive.**
   - In Google Drive, create `My Drive/Raikou_Optical_Phase0/`.
   - Drag this whole `optical_phase0` folder into it, so that `My Drive/Raikou_Optical_Phase0/optical_phase0/raikou_phase0/__init__.py` exists.
   - If you use another location, change `ROOT` in the first cell of each notebook.
2. **Drive space:** about 10 GB in total (5 GB of tiles, 2 GB of checkpoints, about 2 GB for the release folder plus its tar).
3. **Compute units.** Notebook 1 runs on CPU only. Notebook 2's speed probe prints the projected GPU hours; multiply by the rate Colab shows under *Runtime → View resources* (it changes, so read it there rather than trusting a number in this file).
4. **Optional, Copernicus cells only.** Notebook 1 §8 and Notebook 3 §8 need Colab secrets:
   - Open the key icon in the left bar and add `CDSE_CLIENT_ID` and `CDSE_CLIENT_SECRET`.
   - Allow notebook access.
   - Never paste them into a cell. Each run prints its PU estimate first (16.5 PU per 10 × 10 km date; the quota is 10,000 a month, shared with SAR).

To open a notebook, double-click it in Drive and choose *Open with → Google Colaboratory*. Then set the runtime from the table above, and run the cells top to bottom.

## Notebook 1: dataset (CPU)

1. **Steps 1–3:** mount Drive, install, and run the self-test. It should end with `CPU self-test passed.`
2. **Step 4: the manifest.**
   - It is written to `manifests/india_100_tiles.csv` and shown on a map (blue train, amber val, red test).
   - If you edit the CSV, your copy is used from then on.
3. **Step 5: WorldCover preview.**
   - Look at the flagged tiles (mostly water, a single class, much nodata/snow).
   - To move one, edit its row (or the anchor in `tiles.py`), delete the CSV, and re-run step 4.
4. **Step 6: build.**
   - Re-run it until `0 failed`. Finished tiles are skipped.
   - Errors land in `tiles/<id>.error.txt`.
5. **Step 7: check the cleaning.**
   - A warning means a rule removes more than 70 % of a WorldCover class in a zone.
   - Look at that zone's quicklooks (true colour | WorldCover | cleaned labels, black = ignored).
   - If the rule is too strict, loosen it in `CONSENSUS_RULES`, delete those tiles' `.json`, and rebuild.
6. **Step 8 (optional):** parity check, about 50 PU.

## Notebook 2: training (L4)

1. **Steps 1–3:** GPU check, install (keeps Colab's own torch; it must be 2.7 or newer), settings, and the verified base weights.
   - To try `patch_size=2`: `C.TrainConfig(patch_size=2, micro_batch=4, grad_checkpointing=True)`.
2. **Step 4: GPU self-test.**
   - It runs forwards at T = 1/2/3 with clouds, a padding-leak check and a backward pass.
3. **Step 5:** copy the tiles to the VM's local disk.
4. **Step 6: speed probe.** It runs 20 real steps and prints the projected hours and peak VRAM.
   - Decide here, before spending the bulk of the units.
5. **Step 7: train.**
   - One JSON line per epoch.
   - `checkpoints/last_epoch.pt` is copied to Drive after every epoch.
   - **After a disconnect:** reconnect, run steps 1–5, then step 7 again. It resumes after the last finished epoch.
6. **Step 8:** curves and the best epoch's validation mIoU.

## Notebook 3: T4 checks, calibration, demo, export

1. **Steps 1–4:** load the best checkpoint and run the self-test on the T4.
2. **Step 5:** temperature scaling and the reliability plot (`reports/reliability.png`).
3. **Step 6:** the 15-tile benchmark at T=1/T=3, fp32 and fp16.
   - If fp16's mean IoU is more than about 0.005 below fp32's, keep production in fp32.
4. **Step 7: Demo A.** The Visakhapatnam coast tile with an Oct 2025 → May 2026 seasonal stack from Planetary Computer (free). Output: `release_export/demo_visakhapatnam_T3/`.
5. **Step 8: Demo B (optional).** The same tile, one date, fetched from Copernicus exactly as production will (about 16.5 PU).
6. **QGIS check.**
   - Drag `visakhapatnam_lulc_10m.tif` into QGIS; it should open with the five colours and class names (the `.qml` beside it loads automatically).
   - Check for seams, shoreline alignment against a basemap, and polygon areas in the `.gpkg`.
7. **Step 9: export.**
   - Produces `release_export/olmoearth_india_v1_2/` and `olmoearth_india_v1_2.tar` plus its `.sha256`.
   - The release is then reloaded through `infer.load_model` / `infer.predict`, the same calls the backend will use.

### What a demo bundle contains

| File | Content |
|---|---|
| `*_lulc_10m.tif` (+ `.qml`, `.clr`, `.aux.xml`) | Classes 1–5 (0 = no data), native UTM, embedded colour table and class names |
| `*_score_10m.tif` (+ `.qml`) | Calibrated score 0–100 (255 = no data) |
| `*_worldcover2021_10m.tif` | WorldCover 2021, remapped to the same 5 classes, on the identical grid |
| `*_polygons.gpkg` | One polygon per class region: `class_id`, `class_name`, `area_sqkm`, `area_hectares`, `mean_ndvi`, `mean_score_pct` |
| `lulc_stats.csv`, `agreement_matrix.csv` | Areas and shares per class; WorldCover 2021 vs this map in km² (agreement, not change) |
| `*_model_view_pca.png/.tif`, `*_similarity.png/.tif` | Encoder PCA "model view" and cosine similarity to a seed cell (40 m) |
| `VALIDATION_AND_CITATION.txt` | Agreement numbers, what the score means, limits, and the required credits and licences |

## Moving the release to the g4dn box

On Drive, share `release_export/olmoearth_india_v1_2.tar` as *Anyone with the link*. Copy the file ID (the long string in the link), then on the box run:

```bash
python3 -m venv /tmp/gd && /tmp/gd/bin/pip -q install gdown
```

```bash
mkdir -p ~/backend/models && cd ~/backend/models && /tmp/gd/bin/gdown "https://drive.google.com/uc?id=FILE_ID" -O olmoearth_india_v1_2.tar
```

```bash
cd ~/backend/models && tar -xf olmoearth_india_v1_2.tar && cd olmoearth_india_v1_2 && sha256sum -c SHA256SUMS.txt
```

Turn link sharing off again afterwards. `~/backend/models` is excluded from the deploy rsync, so the files survive deploys. Don't install anything into the SAR backend's `sar_env`. Per the approved plan, the optical model gets its own venv and worker (Phases 1–2).

## Troubleshooting

| Symptom | Fix |
|---|---|
| `Upload the optical_phase0 folder…` | The folder is not at `ROOT/optical_phase0`; fix the path or `ROOT`. |
| Planetary Computer / WorldCover timeouts in step 6 | Re-run the cell; finished tiles are skipped. |
| `rule removes >70%` | See Notebook 1 step 7. |
| `CUDA out of memory` | Lower `micro_batch` (gradients accumulate, so the effective batch stays 16), or set `grad_checkpointing=True`. |
| `torch … is older than 2.7` | Colab's image changed. Install a CUDA build of torch ≥ 2.7 that matches Colab's CUDA, then restart the runtime. |
| `OlmoEarth base files do not match` | The download is not the official release. Do not continue; retry with `weights_source='huggingface'`. |
| `last_epoch.pt was trained with another patch_size` | Move `checkpoints/last_epoch.pt` aside to start a fresh run. |
| A bundle says `GTiff (tiled)` instead of `COG` | The COG driver dropped the colour table on that GDAL build. The file is still a valid tiled GeoTIFF with the palette. |
